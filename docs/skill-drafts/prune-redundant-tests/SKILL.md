# 既存テストの重複を減らす

1. 対象テストと実際の呼び出し経路を読み、各アサーションが守る挙動と、それを壊す現実的な変更を対応づける。各候補に、残す・統合する・削るの判断と理由を添える。実行時間、不安定さ、仕様変更時の修正負担は、根拠がある範囲で保証の価値と比較する。
2. 同じ入力と経路で同じ回帰を検出できる場合は、公開インターフェースを通る既存テストへまとめる。異なる失敗経路、境界条件、競合を検出する保証は残す。外部応答のステータスと形式を別々に検証するなら、それぞれ一方だけが無効な応答を使い、別の検証で先に失敗することを防ぐ。
3. 失敗経路の重複を見直す場合は、提案の段階でも、現行テストで一方の検証を外しても他方の失敗で通ってしまう箇所を示す。変更案では、外す検証と失敗するはずのテストを対応づけ、実行可能な確認方法を添える。実装も依頼された場合は、変更前の関連テストの結果を記録し、変更後に同じ範囲を実行する。残したテストが回帰を検出するかコードから判別しづらい場合は、隔離した作業環境で該当する挙動だけを一時的に壊し、期待した理由で失敗するか確かめる。対象テストと全体スイートの結果、既存の失敗、確認範囲を報告する。
